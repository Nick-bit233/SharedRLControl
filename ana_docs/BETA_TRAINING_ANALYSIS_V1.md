## 4. ⚠️ 根本原因分析

### 4.1 【核心bug】`enable_task_reward: False`

**在 `configs/experiment/tunnel.yaml` (基础配置) 中**：

```yaml
env:
  enable_task_reward: False  # ← 所有阶段继承此设置
```

这意味着**速度跟随奖励被完全禁用**。实际奖励函数为：

```python
self.reward = (
    0.0                    # task_reward_term = 0 (DISABLED!)
    + 0.5                  # reward_survival: 每步 +0.5
    + 5.0 * r_safety       # 安全屏障奖励
    - 15.0 * penalty_height # 高度惩罚
)
# 终止奖惩：
# 碰撞: -10.0
# 成功: +10.0
```

**奖励激励分析**：

| 行为策略 | 存活奖励 | 成功奖励 | 安全惩罚 | 总奖励 |
|----------|---------|---------|---------|--------|
| 快速通过（650步成功） | 0.5×650 = 325 | +10 | 低 | ~335 |
| 慢速安全飞行（1000步超时） | 0.5×1000 = **500** | 0 | 极低 | ~**500** |
| 快速但碰撞（400步崩溃） | 0.5×400 = 200 | 0 | 高 | ~50 |

**慢速飞行的奖励（~500）远高于快速通过的奖励（~335）！**

在简单环境（S1-S3, 30-80障碍物）中，人类轨迹的2.0 m/s命令足以让无人机快速通过，无需额外激励。但在密集环境（S4-S5, 120-170障碍物）中：
- 频繁的避障操作本就会降低速度
- 奖励函数告诉策略"活得越久越好"
- 策略学会了"慢速 + 零碰撞"的最优（但错误的）策略

### 4.2 速度差异的物理解释

`debug/vec_policy/x ≈ 2.0` 但 `debug/vec_world/x ≈ 0.75`，这个2倍差异来自多个因素叠加：

1. **密集障碍物 → 频繁横向修正**
   - 每次横向闪避消耗推力预算，降低可用前进推力
   - 障碍物越密，修正越频繁，前进速度越低

2. **速度控制器动态限制**
   - 多旋翼通过倾斜产生水平推力
   - 同时前进 + 横向移动需要更大倾角
   - 控制器有最大倾角限制

3. **命令振荡 → 控制器跟踪失败**
   - S4-S5的smoothness penalty达到0.2-0.5（远高于S1-S3的0.05-0.1）
   - 表明策略命令快速振荡
   - 低空速度控制器无法追踪高频命令变化

4. **没有速度奖励 → 无纠正压力**
   - 即使速度下降，奖励函数不会惩罚
   - 反而因存活更久获得更多奖励

### 4.3 reg_coeff课程失败

S5的reg_coeff课程依赖 `episode/stats_success`（训练时随机采样成功率）作为晋升指标：
- 训练成功率≈0%（因为随机探索 + 慢速 = 超时）
- 晋升阈值 = 95%
- 因此reg_coeff始终停留在初始值0.01，从未提升
- 这是已知bug（应使用 `eval/stats_success`）

## 5. diag_reward_task 下降趋势分析

从图表中可以看到 `episode/stats_diag_reward_task` 在后期阶段持续下降（从0.7降至0.4-0.5）。

`diag_reward_task` 的计算：
```python
reward_task = 1.0 * exp(-2.0 * ‖target_vel - actual_vel‖) + 0.5 * (cosine_sim + 1)/2
```

当 `actual_vel` 远低于 `target_vel` (2.0 m/s) 时：
- `vel_error` 大 → `exp(-2 * error)` → 接近0
- 方向也可能不对齐 → cosine_sim 低

这进一步确认：策略在后期阶段主动放弃了速度跟随。

## 6. 推荐修改方案

### 6.1 🔴 紧急修复：启用速度跟随奖励

**方案A：直接启用 task_reward**
```yaml
# tunnel.yaml
env:
  enable_task_reward: True  # 启用速度跟随奖励
```

**风险**：可能与safety reward产生冲突（快速飞行 vs 安全避障）

**方案B（推荐）：添加前进进度奖励**

在 `env_tunnel.py` 中取消注释并调整前进速度奖励：
```python
# 当前被注释的代码 (line 668-671):
forward_vel = drone_vel_w[..., 0:1]
reward_progress = 0.2 * forward_vel.clamp(min=0.0)  # 仅奖励正向运动
```

将其加入总奖励中。这比task_reward更简洁，直接激励前进。

**方案C（最稳健）：A + B组合 + 降低存活奖励**
```python
self.reward = (
    task_reward_term           # 启用速度跟随
    + 0.2                      # 降低存活奖励（从0.5→0.2）
    + 0.2 * forward_vel.clamp(min=0.0)  # 前进进度
    + 5.0 * r_safety
    - 15.0 * penalty_height
)
# 增大成功奖励
self.reward[success_mask] += 50.0   # 从10提高到50
```

### 6.2 🟡 中期改进

1. **修复reg_coeff课程指标**：使用 `eval/stats_success` 替代 `episode/stats_success`
2. **调整smoothness penalty**：将其纳入奖励函数（目前仅记录不使用）
3. **min_concentration微调**：S4的min_concentration=10可能限制了必要的探索空间

### 6.3 🟢 长期考虑

1. 动态调整max_episode_length：密集环境允许更长episode
2. 分离"避障能力"和"前进能力"的训练目标
3. 考虑将forward_vel作为observation的一部分，让策略意识到自己在减速
